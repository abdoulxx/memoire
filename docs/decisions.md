# Journal des choix techniques

> Un choix = 3 lignes : le choix, les alternatives ecartees, la raison.
> Alimente les justifications du chapitre 4 du memoire (CLAUDE.md §11).

## 2026-10-22 — D01 : gestionnaire d'environnement `uv` + Python 3.11
- **Choix** : `uv` avec `.python-version` = 3.11 (3.11.15 installee par uv), dependances declarees dans `pyproject.toml` et figees dans `uv.lock`.
- **Alternatives ecartees** : `venv` + `pip` + `requirements.txt` (pas de resolution deterministe) ; conda (lourd, non installe) ; Python 3.13/3.14 deja presents sur la machine.
- **Raison** : reproductibilite exigee par le livrable 2 ; 3.11 est la version ciblee par la CI et celle pour laquelle les roues de `river`, `mlflow` et `scikit-learn` sont les plus stables.

## 2026-10-22 — D02 : point d'entree CLI Python au lieu de `make`
- **Choix** : un CLI `mdrift` (Typer), une sous-commande par experience ; le `Makefile` n'est qu'une enveloppe pour la CI Linux.
- **Alternatives ecartees** : `make` seul (absent sous Windows, poste de developpement principal) ; scripts `.ps1` (non portables vers la CI).
- **Raison** : « une commande par experience » doit fonctionner a l'identique sur le poste de developpement et dans la CI.

## 2026-10-22 — D03 : paquet nomme `src`
- **Choix** : les modules sont importes via `src.<module>` ; `pythonpath = ["."]` pour pytest, `packages = ["src"]` pour le build.
- **Alternatives ecartees** : layout `src/memoire_drift/` (plus conventionnel) ; modules a la racine.
- **Raison** : conserver a l'identique l'arborescence decrite dans le cadrage du projet, qui est reprise telle quelle dans le memoire (chapitre 5).

## 2026-10-22 — D04 : dependances installees au fur et a mesure des jalons
- **Choix** : M0 n'installe que numpy, pandas, scikit-learn, scipy, pyyaml, typer, matplotlib, pyarrow. `river` et `mlflow` arrivent a M2/M5.
- **Alternatives ecartees** : installer toute la pile des le depart.
- **Raison** : regle n°1 du cadrage (« le pipeline est un moyen, pas le sujet ») ; chaque dependance doit se justifier au moment ou elle sert, et l'environnement reste rapide a reconstruire.

## 2026-10-22 — D05 : telechargement selectif du SMD plutot que clone du depot
- **Choix** : telechargement fichier par fichier depuis `raw.githubusercontent.com`, limite aux machines listees dans `configs/datasets/smd.yaml` (3 machines = 55,5 Mo), avec manifeste `manifest.json` (taille + SHA-256 de chaque fichier).
- **Alternatives ecartees** : `git clone` du depot OmniAnomaly (environ 500 Mo pour 28 machines, dont du code TensorFlow 1.x inutile) ; versionnement des donnees dans le depot (interdit par le .gitignore et inutile).
- **Raison** : le perimetre de M0-M2 est de 3 machines ; le manifeste rend le jeu de donnees utilise identifiable dans le memoire et verifiable a la reexecution.

## 2026-10-22 — D06 : intervalle d'echantillonnage du SMD fixe a 60 secondes
- **Choix** : `sampling_interval_seconds: 60`. Toutes les metriques temporelles (fausses alertes par heure, delai de detection, temps de recuperation) en decoulent.
- **Alternatives ecartees** : aucune — la valeur n'etait pas documentee dans le README du depot et devait etre etablie.
- **Raison** : source primaire verifiee le 22/10/2026 — Garg et al., *An Evaluation of Anomaly Detection and Diagnosis in Multivariate Time Series*, IEEE Transactions on Neural Networks and Learning Systems 33(6), 2022, doi 10.1109/TNNLS.2021.3105827 : le tableau I donne pour le SMD 28 entites, 38 canaux et un **pas de temps de 60 s**, et le texte precise « 28 entities regularly sampled every minute » sur une collecte de 5 semaines. Verification empirique concordante : machine-1-1 compte 28 479 + 28 479 points, soit 39,6 jours (5,7 semaines) a un point par minute. Source secondaire : Su et al., KDD 2019 (publication d'origine du dataset).
- **Correction** : la premiere version de cette entree citait Kim et al., AAAI 2022, pour l'intervalle. Cet article ne donne aucun intervalle d'echantillonnage et decrit meme le SMD sur 10 jours ; il reste cite ailleurs, pour ce qui est son objet reel (critique du protocole *point-adjust*).

## 2026-10-22 — D07 : un evenement d'anomalie = une plage contigue de points etiquetes 1
- **Choix** : les evenements sont derives de `test_label` par decoupage en plages contigues (`events_from_label`). `interpretation_label` n'est pas utilise pour definir les evenements, mais conserve pour savoir quelles dimensions sont impliquees.
- **Alternatives ecartees** : utiliser directement les plages de `interpretation_label` comme definition des evenements.
- **Raison** : la definition doit decouler des etiquettes qui servent au calcul du rappel par fenetre, pour que les deux familles de metriques reposent sur la meme verite terrain. Controle de coherence effectue : le nombre de plages contigues egale exactement le nombre de lignes de `interpretation_label` sur les trois machines (8, 13 et 4).

## 2026-10-22 — OBS01 : le SMD est deja normalise a la source (limite a declarer)
- **Observation** : les valeurs de `train` et `test` sont deja ramenees dans l'intervalle [0, 1] par les auteurs du dataset, vraisemblablement par une mise a l'echelle min-max calculee sur l'ensemble de la serie.
- **Consequence** : la regle « normalisation ajustee sur les donnees d'entrainement uniquement » s'applique a notre propre standardisation des features derivees (moyennes, ecarts-types, maxima glissants), mais pas a la mise a l'echelle d'origine, qui a deja vu la moitie de test.
- **A declarer** : limite methodologique a mentionner au 6.3.3 du memoire (fuite d'information residuelle, inherente au dataset public et subie par tous les travaux qui l'utilisent). Elle n'avantage aucune des strategies comparees, puisqu'elles partagent exactement les memes donnees d'entree.

## 2026-10-22 — OBS02 : divergence de la litterature sur le nombre de metriques du SMD
- **Observation** : certaines publications decrivent le SMD avec 33 capteurs, d'autres avec 38.
- **Fait verifie localement** : les fichiers telecharges comportent **38 colonnes** (verification automatisee dans `tests/test_smd_loader.py`), sur les 28 machines.
- **Divergence tranchee le 22/10/2026** : le tableau I de Garg et al. (IEEE TNNLS 33(6), 2022) annonce **38 canaux** pour le SMD. Le comptage local n'est donc plus seul : il concorde avec une source citable.
- **A declarer** : annoncer 38 metriques dans le memoire, avec la double justification (comptage direct sur les fichiers du depot officiel + Garg et al., tableau I). Mentionner la valeur 33 presente dans d'autres articles comme une divergence de la litterature, non comme une incertitude de notre part.

## 2026-10-22 — D08 : taille de fenetre w = 10 minutes, pas de 1 minute
- **Choix** : `window_size: 10`, `stride: 1`, agregats `last`, `mean`, `std`, `max` par metrique, soit 152 features par fenetre.
- **Alternatives ecartees** : w = 30 min (rappel par fenetre plus facile a obtenir, donc chiffres moins comparables a la litterature) ; w = 5 min (statistiques glissantes trop bruitees) ; fenetres disjointes (delai de detection mesurable seulement au multiple de w, et ecart avec le mode en ligne).
- **Raison** : mesure de l'effet de dilatation du label, w = 10 ne gonfle le taux de fenetres positives que de 1,03x a 1,12x par rapport au taux de points anormaux (9,46 % -> 9,72 % ; 4,94 % -> 5,43 % ; 1,07 % -> 1,20 %). Le pas de 1 minute rend le mode rejeu strictement coherent avec la boucle en ligne, qui interrogera Prometheus chaque minute.

## 2026-10-22 — D09 : niveau `machine` ajoute dans l'arborescence des resultats
- **Choix** : `results/runs/<source>/<machine>/<scenario>/<strategie>/<seed>/`.
- **Alternatives ecartees** : l'arborescence du cadrage, sans niveau machine.
- **Raison** : la campagne porte sur plusieurs machines SMD ; sans ce niveau, les executions de machines differentes se recouvriraient. Le `run_id` et `summary.csv` portent egalement la machine.

## 2026-10-22 — D10 : scoring par blocs entre deux reentrainements
- **Choix** : le harnais score en un appel toutes les fenetres separant deux reentrainements, puis deroule la boucle de decision sequentiellement.
- **Alternatives ecartees** : un appel a `score()` par fenetre.
- **Raison** : entre deux reentrainements le modele en service est constant, le resultat est donc **exactement identique** au scoring point par point, pour un temps de calcul reduit de plusieurs ordres de grandeur (1,5 s par machine au lieu de plusieurs minutes). La contrainte prequentielle est preservee : la decision reste sequentielle et le reentrainement ne recoit que l'historique deja observe (verifie par test).

## 2026-10-22 — D11 : fausses alertes definies comme les faux positifs par fenetre
- **Choix** : une fausse alerte est une alerte emise sur une fenetre etiquetee negative ; la tolerance d'attribution ne sert qu'au rappel par evenement et au delai de detection.
- **Alternatives ecartees** : definir une fausse alerte comme une alerte non attribuable a un evenement (deux verites terrain concurrentes dans le memoire).
- **Raison** : avec `tolerance = w - 1`, la zone d'attribution d'un evenement coincide exactement avec les fenetres positives qu'il engendre ; les trois familles de metriques reposent alors sur une seule et meme verite terrain. Propriete verifiee par test (`test_coherence_des_trois_familles`).

## 2026-10-22 — OBS03 : derive naturelle entre les deux moities du SMD (resultat majeur)
- **Observation** : le seuil est calibre pour 1 % d'alertes sur les donnees d'entrainement. Sur la moitie `test`, le modele fige produit 12,88 % d'alertes (machine-1-1), 2,24 % (machine-2-1) et **45,38 %** (machine-3-1), soit 12,9x, 2,2x et 45,4x le taux de calibrage. La mediane des scores monte systematiquement entre les deux moities (ex. 0,4404 -> 0,5402 sur machine-3-1).
- **Interpretation** : les deux moities du SMD ne suivent pas la meme distribution. Une derive de concept **naturelle** existe donc dans le dataset, sans aucune injection de notre part. Sur machine-3-1, le modele fige finit totalement inutilisable.
- **Forme du profil, re-mesuree le 22/10/2026 apres correction de la methode** : moyenne glissante **causale** sur 500 fenetres (aucune information posterieure a l'instant date) du taux de **fausses alertes seules**, c'est-a-dire des alertes emises sur des fenetres etiquetees negatives. Premiers depassements :

  | niveau | machine-3-1 | machine-1-1 |
  |---|---|---|
  | 1 % | 22,1 h | 8,3 h |
  | 5 % | **93,5 h** | 62,8 h |
  | 25 % | 118,1 h | 64,5 h |
  | 50 % | 182,0 h | 208,1 h |
  | 90 % | 314,1 h | jamais |

  Profil de machine-3-1 par tranches de 10 h, taux de fausses alertes en pourcentage : 0,3 / 0,0 / 3,3 / 0,2 / 2,0 / 0,3 / 1,0 / 0,5 / 0,0 / **12,3 / 11,3 / 24,2** / 6,2. Les fausses alertes restent donc proches du taux calibre de 1 % jusque vers 90 h, avec quelques rafales passageres, puis la degradation devient durable ; la saturation depasse 90 % au-dela de 310 h. machine-1-1 a un profil tout autre : sa premiere anomalie etiquetee n'arrive qu'a 264 h, toutes ses alertes anterieures sont donc fausses, et elles arrivent par bouffees isolees (29,2 % entre 60 et 70 h, 0 % de 70 a 110 h, 11,0 % entre 110 et 120 h) sans jamais saturer. La figure `taux_alertes_machine-3-1_none_static_seed42.png` illustre le premier cas.
- **Formulation a reprendre dans le memoire** : fausses alertes proches du taux calibre jusque vers **90 h** sur machine-3-1, puis degradation durable, saturation au-dela de **310 h**, avec des profils de derive naturelle **heterogenes selon la machine**.
- **Correction de methode (deux erreurs successives, signalees par la relecture du memoire)** : la deuxieme version de cette entree annoncait une degradation amorcee des **16 h**. C'etait un artefact de mesure, produit par deux defauts cumules. (1) La moyenne glissante etait **centree** : elle attribuait a l'instant t une information issue de t + 250 fenetres, soit une anticipation de 4,2 h. Verifie par la mesure : 16,0 h en centre contre 20,1 h en causal, et un ecart de +4,1 a +4,2 h a tous les niveaux de la table. (2) Elle comptait **toutes** les alertes : le premier depassement a 20,1 h coincide exactement avec l'anomalie etiquetee 20,1 h - 20,6 h, c'etait donc une detection reussie, pas une derive. En ne comptant que les fausses alertes et en moyenne causale, le seuil de 5 % n'est franchi qu'a 93,5 h, juste apres l'anomalie 90,0 h - 92,2 h. **La description initiale (proche de zero jusque vers 90 h, puis montee) etait donc la bonne** ; c'est le chiffre de 16 h qui est retire. Le message du commit `26fa84a`, qui porte la valeur de 90 h, n'a par consequent pas a etre corrige.
- **Garde-fous ajoutes pour que l'erreur ne revienne pas** : `configs/screening.yaml` impose `rolling.position: causal` et `rolling.counted_alerts: false_only`, et toute autre valeur leve une erreur au lieu d'etre silencieusement acceptee ; `tests/test_screening.py::test_non_regression_obs03` reproduit le piege sur un flux synthetique et verifie que la mesure retenue date la derive **apres** son debut reel, la ou la mesure initiale la datait pendant l'anomalie etiquetee. Lecon generale, a redire au 6.3.3 : tout lissage utilise pour dater un evenement doit etre causal, et toute mesure de derive doit etre separee de la verite terrain des anomalies.
- **Portee pour le memoire** : c'est une justification empirique de la problematique, obtenue sur donnees reelles publiques et non sur un cas construit. A exploiter au 6.2.1 et en introduction.
- **Consequence methodologique** : les scenarios S1 a S4 (M1) s'ajouteront a cette derive naturelle. Il faudra le dire explicitement et, a M2, quantifier la derive naturelle avec les memes detecteurs (PSI, KS, ADWIN) que ceux de la strategie proposee.

## 2026-10-22 — OBS04 : la derive naturelle du SMD n'est pas uniforme (15 machines sur 28 sont stables)
- **Observation** : sur les 28 machines, rapport entre le taux d'alertes de B0 sur la moitie `test` et le taux calibre de 1 % : mediane **3,84x**, min **0,59x** (machine-3-3), max **63,81x** (machine-1-6). Metriques brutes avec KS(train, test) > 0,5 : mediane 1 sur 38, min 0, max 14 (machine-3-1 et machine-3-9). Mesure reproductible par `uv run mdrift smd-screening`, qui ecrit `results/smd_screening.csv` (D20).
- **Critere de stabilite, corrige le 22/10/2026** : une machine est stable si son taux de **fausses alertes** reste sous 3 fois le taux calibre, et non son taux d'alertes total. Meme raison qu'en OBS03 : une alerte sur une fenetre positive est une detection reussie et ne temoigne d'aucune derive. Le critere initial, fonde sur le taux total, classait machine-3-10 instable (3,95x) alors que ses fausses alertes ne representent que **0,45 %**, soit 0,45x le taux calibre : ses alertes sont presque toutes de vraies detections. Avec le critere corrige, **15 machines sur 28 sont stables** (machine-1-2, 1-3, 1-4, 1-7, 2-1, 2-2, 2-3, 2-4, 2-5, 2-7, 3-2, 3-3, 3-4, 3-7, 3-10) au lieu de 13 : machine-2-2 et machine-3-10 rejoignent le groupe. Le critere est explicite dans `configs/screening.yaml` (`stability.basis`) et la colonne `critere_stabilite` du CSV le rappelle a cote de chaque ligne.
- **Observation liee** : le rapport d'alertes et le KS ne mesurent pas la meme chose (Spearman = +0,25). machine-3-5 a un rapport de 32,74x avec **zero** metrique au-dela de KS 0,5 ; machine-3-2 a 5 metriques au-dela de 0,5 pour un rapport de 0,87x.
- **Consequence methodologique** : (a) la campagne S1-S4 de M1-M3 portera sur des **machines stables**, pour que la derive injectee domine et que t_d soit l'unique instant de rupture ; les 13 machines instables sont traitees separement comme cas de derive naturelle et servent de perimetre de mise au point (D17) ; (b) a M2, appliquer PSI et KS aux **152 features**, pas aux 38 metriques brutes : la derive qui degrade le modele est dans la distribution jointe, pas lisible metrique par metrique.
- **Portee pour le memoire** : OBS03 se generalise sans etre uniforme. A dire tel quel, c'est plus credible qu'une affirmation globale.

## 2026-10-22 — OBS05 : le taux d'alertes seul ne distingue pas une anomalie longue d'une derive
- **Observation** : un moniteur naif (taux d'alertes glissant >= 5x le taux calibre pendant K = 30 fenetres) confirme une derive sur **28 machines sur 28**, y compris sur celles dont la moitie `test` est stable. machine-3-3, la plus stable du dataset (0,59x), declenche a 176,5 h : une rafale d'anomalies suffisamment longue suffit.
- **Le defaut survit a la correction d'OBS03** : en passant a une moyenne causale et aux fausses alertes seules, donc en retirant toute contribution des anomalies etiquetees, le meme moniteur confirme encore une derive sur **26 machines sur 28, dont 13 des 15 machines stables**. Seules machine-1-7 et machine-3-7 ne declenchent jamais. Le probleme n'etait donc pas la confusion avec les anomalies : c'est le **niveau de persistance** qui est trop faible, K = 30 fenetres ne valant que 30 minutes. Mesure produite par `mdrift smd-screening`, colonne `derive_confirmee_heures`.
- **Consequence pour la strategie P** : K = 30 fenetres (30 minutes) est beaucoup trop permissif. La confirmation doit se fonder sur la **distribution des features** (PSI, KS), le taux d'alertes n'etant qu'un signal secondaire ; a defaut, K doit valoir plusieurs heures. Valeurs a fixer dans `configs/drift.yaml` a M2, avec cette mesure comme justification.
- **Portee pour le memoire** : argument empirique en faveur de l'etape 1 de P telle qu'elle est decrite au cadrage, et contre toute version simplifiee du moniteur.

## 2026-10-22 — OBS06 : les machines d'un meme groupe SMD ne sont pas independantes
- **Observation** : correlation moyenne par metrique entre moities `train` : machine-3-1 vs machine-3-9 **+0,801** ; machine-1-3 vs 1-4 +0,593 ; machine-2-5 vs 2-7 +0,560 ; temoin inter-groupe machine-1-1 vs machine-2-1 **-0,008**. Les paires concernees ont des profils presque identiques (3-1 et 3-9 : rapports 45,38x et 44,56x, 14 metriques KS > 0,5 chacune, confirmation a 21,1 h et 20,8 h, 4 evenements chacune).
- **Consequence** : 28 machines ne sont pas 28 repetitions independantes. Moyenner sur les 28 et appliquer un Wilcoxon apparie sur machines x graines surestimerait la puissance statistique. A M3 : agreger par groupe, ou declarer la limite au 6.3.3.

## 2026-10-22 — D13 : aucune exclusion d'anomalies au reentrainement (etape 3 de P)
- **Choix** : `retrain.exclusion.method: none` par defaut. Variante `top_percentile` (1 %) conservee comme option d'ablation : c'est la seule concurrente credible. La variante exclure toutes les fenetres en alerte du champion est implementee pour l'ablation mais **ne doit pas etre utilisee**.
- **Alternatives ecartees** : exclure toutes les alertes du champion ; n'exclure que les rafales plus courtes que K fenetres.
- **Raison** : mesure refaite le 26/10/2026 sur les **16 machines de mise au point** (`mdrift calibration`, `results/calibration_dev.csv`) : 78 instants de reentrainement, 8 regles candidates, W = 2 000 fenetres, V = 500, 3 graines, soit 473 challengers entraines et evalues en aval. Ne rien exclure est la **regle optimale 43 fois sur 78**, ecart median au meilleur **0,0000** et ecart moyen **0,0396** point de F1 : aucune autre regle ne fait mieux sur ces deux agregats. Face a sa seule concurrente, `top_percentile` a 1 %, elle gagne 52 decisions sur 78 contre 24 (Wilcoxon apparie sur les 76 differences non nulles, **p = 0,0040**). Exclure toutes les alertes du champion est la pire regle : optimale 19 fois sur 76, ecart moyen 0,1059, elle perd plus de 0,10 point de F1 sur 24 decisions et **s'effondre sous la moitie du F1 sur 11** (machine-3-1 a 80 % du flux : elle ne garde que 25,3 % de la fenetre et donne F1 0,0615 contre 0,5527, soit x0,11 ; le challenger herite de la saturation du champion, 73,7 % d'alertes et 42,8 fausses alertes/h). Explication de la robustesse de `none` : l'Isolation Forest avec `max_samples: 256` est concu pour tolerer la contamination, et le taux de fenetres positives en aval reste modere (median 5,5 %).
- **Correction d'une mesure anterieure** : la version du 22/10 affirmait que ne rien exclure etait *equivalent* a la meilleure regle, ecart maximal 0,011 point de F1. C'etait un artefact de la mesure sur une seule machine. Sur les 16 machines, l'ecart au meilleur depasse 0,10 point de F1 sur **9 decisions sur 78** et atteint **0,7324** (machine-1-6 a 80 % du flux : F1 0,0771 sans exclusion contre 0,8095 en excluant les 5 % de scores les plus eleves). **Aucune regle ne domine partout** ; `none` est le meilleur choix par defaut, pas un choix sans cout.
- **A exploiter au memoire** : resultat negatif a presenter comme tel. L'etape d'exclusion, intuitive au cadrage, n'apporte rien en moyenne, sa version agressive nuit gravement, et son interet residuel est limite a quelques instants que rien ne permet d'identifier sans etiquettes. Tableau du chapitre 6 : les 8 regles, ecart median et ecart moyen au meilleur, nombre de fois optimale, nombre d'effondrements.

## 2026-10-26 — OBS08 : reentrainer a un instant arbitraire n'est pas un gain, l'instant fait tout
- **Observation** : sur les 78 decisions de `results/calibration_dev.csv`, le challenger sans
  exclusion ne bat le champion fige que **43 fois sur 78**, rapport de F1 median **x1,04**
  (premier quartile 0,85, troisieme quartile 1,37, de x0,08 a x12,13). Le resultat depend
  massivement de l'instant et de la machine : a l'instant que donnerait le moniteur naif
  (taux d'alertes, K = 30), le challenger ne gagne que **3 fois sur 14**, rapport median
  **x0,78** ; a 80 % du flux, 10 fois sur 16, rapport median x1,38. Par machine : x5,13 sur
  machine-3-1 et x3,42 sur machine-3-9, mais x0,32 sur machine-3-10 et x0,76 sur machine-3-8.
- **Consequence** : deux consequences directes pour le memoire. (1) Le chiffre x7,4 mesure le
  22/10 sur machine-3-1 a 400 h est un cas favorable, pas une regle : il ne doit **pas** etre
  presente comme le gain du reentrainement. (2) Reentrainer trop tot nuit, et le moniteur naif
  declenche precisement trop tot (D19). C'est l'argument empirique le plus direct en faveur de
  l'etape 2 de la strategie proposee : la valeur de P n'est pas de reentrainer, c'est de
  reentrainer **au bon moment**. H1 et H2 doivent donc etre testees contre B1 (periodique) et
  non seulement contre B0.
- **A exploiter au memoire** : figure du chapitre 6, rapport de F1 challenger/champion en
  fonction de l'instant de reentrainement, un point par machine. Et une phrase au 6.3.3 : un
  reentrainement declenche au hasard est un pari a somme a peu pres nulle sur ce jeu de donnees.

## 2026-10-22 — D14 : la validation de P est un garde-fou, pas un concours (etape 4)
- **Choix** : l'etape 4 rejette un challenger aberrant au lieu de le comparer au champion. Criteres, tous sans etiquettes : moins de `min_train_windows` fenetres utilisables ; taux d'alertes sur la fenetre reservee hors de [`alert_rate_min`, `alert_rate_max`] ; seuil degenere (>= max des scores d'entrainement). Sinon, promotion.
- **Bornes du garde-fou, calibrees le 26/10/2026** sur les 473 challengers du perimetre de mise au point (285 sains, 188 degrades au sens d'un F1 aval a plus de 0,05 du meilleur de leur instant). Valeurs retenues, et elles ne sont pas celles du cadrage :
  - `min_train_windows: 256`, soit `max_samples` du modele. Entrainer une foret sur moins de fenetres que son propre echantillon n'a pas de sens. Seule borne deduite du modele et non des donnees.
  - `alert_rate_min: 0.0`, c'est-a-dire **borne basse desactivee**. Le cadrage proposait 0,1 %. Or **98 challengers sur 473 n'alertent sur aucune fenetre reservee**, et 63 d'entre eux sont sains, avec un F1 aval median de **0,4202** contre 0,2605 pour l'ensemble. Un taux d'alertes nul sur V n'est pas un defaut : il signifie le plus souvent que la fenetre reservee ne contient pas d'anomalie. Rejeter sur ce critere ecarterait les meilleurs challengers.
  - `alert_rate_max: 0.90`. Le cadrage proposait 30 % : cette borne rejetterait **37 challengers sains sur 285** pour seulement 22 degrades sur 188, elle fait donc plus de mal que de bien. Les challengers sains vont jusqu'a **87 %** d'alertes sur V, legitimement : sur machine-1-6 a 80 % du flux, 60,1 % des fenetres aval sont reellement positives. Seule une borne a 0,90 ne rejette **aucun** challenger sain, tout en ecartant 5 degrades (F1 aval median 0,3583), dont un challenger qui alerte sur **100 %** de la fenetre reservee.
- **Consequence assumee : le garde-fou ne rejette que 5 candidats sur 473, soit 1,1 %.** C'est la mesure, pas un reglage timide : aucune borne intermediaire ne separe les deux populations (a 0,30 comme a 0,50, elle rejette autant de sains que de degrades). Il faut donc l'ecrire ainsi au memoire : en rejeu, l'etape 4 est un filet de securite contre l'aberrant, et **A1 devrait egaler P** ; c'est une prediction testable, pas une excuse. L'apport de l'etape 4 est a chercher en mode en ligne (M5), ou un modele degenere promu reste en service jusqu'a la prochaine confirmation, et ou la validation humaine du bonus s'y rattache.
- **Alternatives ecartees** : taux d'alertes le plus proche du taux calibre de 1 % (le critere envisage au cadrage) ; KS entre scores d'entrainement et scores de validation.
- **Raison** : mesure refaite le 26/10/2026 sur les 16 machines de mise au point, 71 decisions comportant au moins trois challengers distincts. Le critere n'est pas inverse, il est **inexploitable** : Spearman median entre l'ecart au taux cible et le F1 aval **-0,66** (on attend du negatif, donc le sens est le bon), mais le signe s'inverse sur **18 decisions sur 71** ; pour le KS entre scores d'entrainement et de validation, median -0,55 et 18 inversions. Choisir le challenger par ce critere coute **5,1 % du F1 atteignable en median, jusqu'a 100 %**, et selectionne le **pire** candidat de la decision **11 fois sur 71**, soit une fois sur six. Un critere qui va dans le bon sens en moyenne mais se trompe completement une fois sur six ne peut pas arbitrer une mise en service automatique.
- **Correction d'une mesure anterieure** : la version du 22/10 concluait que les deux criteres correlaient dans le **mauvais** sens (+0,30 et +0,60 sur machine-1-1, +0,90 sur machine-2-1). Cette mesure etait doublement fautive : elle incluait machine-2-1, machine d'evaluation, et elle ne visitait qu'un instant de reentrainement par machine, ou les regles d'exclusion gardent les memes fenetres et produisent donc le meme modele plusieurs fois, ce qui gonflait la correlation par des ex aequo. La conclusion pratique est inchangee, sa formulation non : **on ne dira pas que le critere est inverse, on dira qu'il est trop instable pour classer**.
- **Appui bibliographique** : ce resultat negatif rejoint la litterature. Ma, M. Q., Zhao, Y., Zhang, X., & Akoglu, L. (2023). *The Need for Unsupervised Outlier Model Selection: A Review and Evaluation of Internal Evaluation Strategies*. ACM SIGKDD Explorations Newsletter, 25(1) ; doi 10.1145/3606274.3606277. Leur etude a grande echelle associee (*A Large-scale Study on Unsupervised Outlier Model Selection: Do Internal Strategies Suffice?*, arXiv:2104.01422) conclut textuellement qu'aucune des strategies internes evaluees ne serait utile en pratique, car elles selectionnent des modeles seulement comparables a un detecteur de l'etat de l'art configure au hasard (« none would be practically useful, as they select models only comparable to a state-of-the-art detector (with random configuration) »). Notre mesure est un cas particulier de ce constat, sur des donnees de metriques serveur. [A VERIFIER] pagination 19-35 non confirmee sur la source primaire (ACM renvoie une erreur 403) : a verifier avant citation definitive.
- **Consequence** : sans etiquettes on ne peut pas classer des challengers sur la qualite de detection de maniere fiable. Le filet de securite reel est la confirmation sur K fenetres en amont (OBS08 : reentrainer trop tot nuit) et le refroidissement C en aval. Ce que la validation apporte doit etre **mesure** par l'ablation A1, non suppose, et les bornes calibrees ci-dessus rendent probable qu'A1 egale P en rejeu. En mode en ligne (M6), les pannes injectees sont horodatees : un critere a etiquettes retardees y est possible, ecart a discuter au 6.3.3.

## 2026-10-22 — D18 : agregation des tests de derive sur les 152 features par la part de features en derive

Des que plus de la moitie des paires sont a egalite — le cas normal pour `n_promotions_degradantes`, nulle sur **42 paires sur 48** —, la mediane des differences vaut 0 alors que Wilcoxon, qui **ignore les ex aequo**, mesure une direction nette. H3 s'affichait donc « contraire a l'attendu » (p Holm 0,0235) alors que P fait **mieux** que A1 : le tableau annoncait l'inverse du test, sur l'hypothese qui porte la contribution du memoire. La direction est desormais lue sur le **signe de la somme des rangs signes**, c'est-a-dire la statistique du test elle-meme, et `results/hypotheses.csv` publie le compte `+/-` des ecarts non nuls pour qu'elle soit verifiable sans refaire le calcul. Un test de non-regression fixe le comportement (20 machines dont 9 a ecart non nul : il faut au moins 6 ecarts non nuls pour descendre sous p = 0,05 et une majorite d'ex aequo pour que la mediane soit nulle, ce qui est impossible a 12 machines).
- **Mediane et moyenne sont rapportees ensemble** dans `docs/tableaux_chapitre6.md`, parce que les deux se contredisent parfois : sur `f1_after` contre B1, la mediane met P devant (0,312 contre 0,298) et la moyenne le met derriere (0,309 contre 0,324), le test ne concluant a aucune difference. Citer une seule des deux laisserait croire a un ecart non significatif.
- **A exploiter au memoire** : le protocole va au 6.1 (methodologie de test) ; le piege de la mediane va au 6.3.3 comme limite de methode rencontree et corrigee.

La part reellement interpolee est rapportee par metrique.
- **Une anomalie plus courte que le pas est signalee, pas ignoree** : elle serait invisible dans les donnees tout en comptant comme un evenement a detecter, ce qui ferait baisser le rappel par evenement de **toutes** les strategies sans qu'aucune puisse y faire quoi que ce soit. De meme, une anomalie ou une derive dans la part d'entrainement fait **echouer** le chargement : un modele initial entraine sur une anomalie ne la signalera jamais, et la comparaison des strategies qui en decoule ne veut plus rien dire.
- **Defaut trouve par les tests** : `float("+Inf")` et `float("NaN")` **reussissent**. Le code comptait sur une exception pour ecarter les valeurs non finies que Prometheus rend en texte, et les laissait donc passer. Un `histogram_quantile` sur un bucket vide rend `NaN`, une part calculee sur un denominateur nul rend `+Inf` : un seul `inf` dans une colonne traverse la normalisation et rend la **session entiere** inexploitable, sans que rien ne le signale. Les valeurs non finies comptent desormais comme des points absents.
- **Deux refus assumes** : une expression PromQL qui rend plusieurs series est **refusee**, avec les etiquettes des series en cause — prendre la premiere serait un choix arbitraire fait par la bibliotheque a la place de l'experimentateur ; et la fenetre des `rate(...)` est fixee dans la configuration, pas laissee a `$__rate_interval`, que Grafana adapte au niveau de zoom — bon pour l'œil, inacceptable pour une mesure.
- **A exploiter au memoire** : les quatre regles d'alignement vont au 5.2 et la justification de l'enregistrement-puis-rejeu au 4.2 ; le defaut des valeurs non finies et la limite des anomalies plus courtes que le pas vont au 6.3.3.

## 2026-11-12 — D42 : les notifications sont construites depuis le journal, et seules des cles declarees en sortent
- **Choix** : `NotificateurTelegram` est un **second abonne** du journal d'evenements. Un message n'existe nulle part dans le code : il n'y a que des evenements journalises dont certains sont pousses. - **Raison de la liste blanche, et c'est le point le plus grave du module** : des que la boucle journalise une erreur de collecte ou de registre, `details` contient une URL, un chemin ou un message d'exception — donc un nom d'hote. Un formateur generique les pousserait vers un **serveur tiers**, ce que le §4.3 interdit sans condition, et une fuite vers l'API Telegram n'est **pas rattrapable** : le message est parti. La liste blanche inverse la charge : une cle non declaree ne sort pas, meme ajoutee plus tard dans la boucle. Un test l'attaque directement, en journalisant un nom d'hote, une adresse IP, un chemin et une URL puis en verifiant qu'aucun n'apparait dans ce qui part.

Les evenements en attente sont agreges en un resume ou **le compte precede le detail** (« 39 anomalies en 60 s. Derniere : ... »), parce que c'est le compte qui decide d'agir. Le rincage a donc lieu **a chaque tick, avant toute sortie anticipee**, et il est **force** a l'arret : sans le premier, le dernier evenement d'une rafale attendrait le prochain du meme type ; sans le second, le resume de session — le message qui clot une demonstration — ne partirait jamais.
- **Raison de l'absence de `parse_mode`** : en Markdown comme en HTML, un `_`, un `*` ou un `<` dans un identifiant de version ou un message d'erreur fait rejeter l'appel avec un 400. La notification serait perdue **au moment ou elle importe le plus**, et pour une raison de mise en forme.
- **Raison du comptage des echecs** : une coupure de reseau mobile ne doit pas arreter un service de detection. Mais un silence de Telegram ne doit pas non plus passer pour « aucun evenement » : le decompte des envois et des echecs s'affiche a l'arret, et `mdrift notify-test` verifie le chemin reel — meme redaction, meme transport — avant une demonstration, comme `session-check` pour la collecte et `registry-info` pour le registre.
- **Trois evenements volontairement non pousses**, justifies dans le fichier de configuration : `drift_signal` (present a chaque fenetre pendant des heures sans confirmation), `retrain_start` (toujours suivi d'un `retrain_end` ou d'un rejet quelques secondes plus tard) et `window_skipped` (un scrape rate coute une fenetre et se lit dans Grafana). Pousser les trois rendrait la conversation illisible, donc inutilisable comme capture.
- **A exploiter au memoire** : le role des notifications va au 5.2 et les captures au chapitre 5 ; la liste blanche repond a la contrainte de securite du 2.3 et merite une phrase explicite, un jury pouvant legitimement demander ce qui sort du serveur vers un service tiers.

Ces trois controles sont des **cibles du Makefile** (`lint`, `test`, `build`), et les fichiers de CI ne font que les appeler. Le depot porte **deux** declencheurs : `.gitlab-ci.yml`, le livrable demande par le cadrage, et `.github/workflows/ci.yml`, celui qui s'execute.
- **Pourquoi deux fichiers** : le cadrage (§10, M7) demande GitLab CI, et le memoire le decrit ainsi. Mais le depot est heberge sur **GitHub** (`origin` verifie), ou un `.gitlab-ci.yml` ne declenche **rien**. Avec ce seul fichier, le jalon M7 ne produirait aucune capture de pipeline — qui est precisement son livrable. Avec le seul fichier GitHub, le depot ne contiendrait pas ce que le memoire annonce. Les deux existent donc, et le memoire doit dire laquelle des deux a produit la capture : c'est une difference entre le cadrage et la realisation, pas un detail de mise en œuvre.
- **Alternatives ecartees** : migrer le depot vers GitLab a trois semaines de la soutenance (l'historique, les URL deja citees et les sauvegardes changeraient de place, pour un gain cosmetique) ; ne garder que `.gitlab-ci.yml` et presenter une capture de l'interface GitLab obtenue sur un depot miroir cree pour l'occasion (ce serait une capture d'un pipeline qui n'a jamais verifie le code livre) ; ne garder que GitHub Actions et corriger le cadrage (possible, mais le cadrage est la reference du memoire : on y deroge en le disant, pas en le reecrivant) ; recopier les commandes dans les deux fichiers plutot que d'appeler `make`.
- **Pourquoi le Makefile est la definition** : deux fichiers qui decrivent le meme controle divergent en silence. C'est exactement le defaut de **D43**, ou une valeur calibree dans une decision et une autre valeur figee dans une configuration paraissaient coherentes prises separement. `tests/test_ci.py` tient l'invariant : les trois cibles existent et sont `.PHONY`, les deux CI les appellent, les deux epinglent la **meme** version de `uv`, les deux installent depuis `uv.lock` avec `--frozen`, aucune ne lance `campaign` ni `smd-download`, aucune ne pousse vers un registre, et les deux fichiers sont du YAML valide — un `.gitlab-ci.yml` casse ne se verrait autrement qu'au prochain push sur GitLab, que personne ne fera avant la soutenance.
- **Pourquoi le troisieme controle est l'installation du paquet et non la seule construction du wheel** : `uv build` reussit presque toujours. Ce qui casse en pratique est le **contenu** du paquet. `pyproject.toml` declare `packages = ["src", "infra"]` parce que le CLI importe `infra.injector` (commandes `chaos*`) : un wheel qui n'embarquerait que `src` s'installerait sans erreur et echouerait a la premiere commande d'injection — celle qui sert a produire les anomalies du chapitre 6. La cible installe donc le wheel dans un environnement neuf et appelle le point d'entree **depuis le dossier d'installation**, pour qu'aucun import ne puisse passer par les sources du depot. Verifie : 50 fichiers sous `src/`, 23 sous `infra/`, `mdrift --help` repond, `import src.cli, infra.injector` passe.
- **Ce que la CI ne fait pas, et c'est voulu** : elle **ne rejoue pas** la campagne M3 (plusieurs heures de calcul) et **ne telecharge pas** le SMD (§4 : les donnees ne sont pas dans le depot, et le §4.3 interdit qu'une trace entre dans un agent). Le seul test qui exige le SMD se declare `skipped` au lieu d'echouer, ce qui est le comportement correct : une CI rouge pour une donnee absente devient une CI qu'on cesse de lire. La reproductibilite des chiffres n'est donc **pas** garantie par la CI mais par `uv.lock` et par les configurations sauvegardees a cote de chaque execution ; un test de rejeu verifie en revanche que la meme graine donne le meme resultat.
- **Deux details d'agent** : `MPLBACKEND=Agg`, sans quoi matplotlib cherche un affichage ; `uv` epingle a **0.11.18**, la version du poste de developpement, parce qu'une CI qui resout les dependances autrement que le poste ne prouve rien sur ce qui a produit les resultats (meme raisonnement que D24). `uv sync --frozen` echoue si `uv.lock` ne correspond plus a `pyproject.toml`, ce qui est le garde-fou voulu et non une optimisation de cache.
- **L'image du service de detection** est construite par un etage **conditionnel** (GitLab, `rules: changes` sur le Dockerfile, `pyproject.toml` et `uv.lock`, sinon manuel) : elle installe une cinquantaine de paquets et n'a rien a verifier si rien de ce qui la definit n'a bouge. Elle n'est **jamais poussee** vers un registre — le §4.3 interdit qu'un artefact de ce depot atterrisse sur un registre public, et le serveur construit son image localement.
- **A exploiter au memoire** : les trois controles et leur justification vont au 5.3 (mise en œuvre) ; la capture du pipeline vert illustre le chapitre 5 ; l'ecart entre le cadrage (GitLab) et l'hebergement (GitHub) se declare au 6.3.3 ou au 7.3, en une phrase, avec la raison du choix. Ce que la CI **ne** verifie pas appartient aussi aux limites : un jury qui voit « CI » peut croire que les resultats sont reproduits a chaque commit.

## 2026-11-14 — D45 : les trois metriques hote sont retirees des features du serveur ; le reseau passe par conteneur
- **Constat** : `docker ps` sur le serveur personnel (`sidy-dev`, 14/11/2026) montre une vingtaine de conteneurs sans rapport avec le memoire — plusieurs applications de clients et personnelles, chacune deployee independamment. Geler tout deploiement sur chacune pendant les dix jours d'enregistrement du §4.2 n'est pas tenable : ce n'est pas un serveur de demonstration dedie, c'est un serveur de production partage, et ces applications tournent en continu pour des tiers.
- **Choix** : `cpu_hote`, `memoire_hote` et `charge_hote` (`node_exporter`, sans filtre par conteneur) sont retirees de `configs/datasets/serveur.yaml` — elles n'alimentent donc plus les features ni la surveillance de derive. `reseau_entrant` / `reseau_sortant` restent des features mais passent de `node_exporter` (hote entier) a `container_network_receive_bytes_total{name="memoire-app"}` / `transmit_bytes_total{name="memoire-app"}` (cAdvisor) : chaque conteneur Docker a sa propre paire veth, ce trafic est donc deja isole des vingt autres conteneurs, pour la meme raison que `cpu_appli` / `memoire_appli` (deja par conteneur depuis la phase B). `disque_libre_pct` reste, hote entier, mais `obligatoire: false` et de toute facon hors du perimetre d'une derive au sens du §5 : son niveau ne bouge pas a chaque deploiement voisin, seulement en cas de fuite disque reelle.
- **Alternatives ecartees** : garder les trois metriques hote et exiger un gel total des vingt conteneurs (irrealiste, et le §4.3 l'aurait de toute facon rendu caduc a la premiere exception documentee) ; deplacer l'enregistrement sur un serveur dedie neuf (cout et delai non justifies a trois semaines de la soutenance, pour un signal que le conteneur isole fournit deja) ; garder les trois metriques hote comme colonnes informatives mais les exclure du calcul des features (demanderait une distinction supplementaire entre « colonne enregistree » et « colonne feature » que rien d'autre dans le pipeline ne porte, pour un gain nul puisqu'elles ne servent a rien d'autre).
- **Raison** : une fenetre devient une feature exactement de la meme facon qu'une metrique en entre dans `configs/features.yaml` — aucune metrique hote ne peut donc rester a moitie dans le flux sans contaminer le moniteur de derive (`drift.yaml`, combinaison `features`) avec l'activite d'applications hors perimetre. Les features necessaires a la question du memoire (CPU, RAM, reseau, requetes, latence, erreurs de **l'appli de test**) ont toutes un equivalent par conteneur ou sont deja par construction propres a l'appli (`app_requests_total`, etc.) : rien n'est perdu sur l'objet etudie, seul le bruit des locataires voisins est coupe.
- **Consequence operationnelle** : la seule contrainte de deploiement qui reste pour les dix jours d'enregistrement est de ne pas toucher au conteneur `memoire-app` lui-meme (ni ses limites de ressources). Les vingt autres applications peuvent etre deployees normalement ; un deploiement chez elles ne traverse plus les colonnes enregistrees. Risque residuel, rare et a surveiller plutot qu'a bloquer : un epuisement reel des ressources de l'hote (disque plein, OOM hote, contention CPU extreme sur vingt conteneurs a la fois) peut encore faire fuiter un effet dans le cgroup de `memoire-app` — `disque_libre_pct` et une verification occasionnelle (`docker stats`, `uptime`) suffisent a le detecter sans en faire une feature.
- **Test touche** : `test_la_configuration_reelle_se_lit_et_decrit_les_metriques_du_tableau_de_bord` verifiait la presence de `cpu_hote` ; corrige pour verifier `cpu_appli`, qui reste dans la configuration.
- **A exploiter au memoire** : le 6.1 doit decrire la session comme enregistree sur un serveur de production partage et non un serveur dedie — c'est une donnee plus realiste pour le chapitre 6, pas une faiblesse a cacher ; le 6.3.3 cite ce choix comme la facon dont l'isolation par conteneur a ete obtenue sans serveur dedie ; le 2.3 (securite) gagne une phrase sur le fait que seul le conteneur de l'experience est sous contrainte de gel, pas l'hote entier.
- **Complement du 15/11/2026, apres inspection de `docker stats` sur le serveur reel** : les applications de production qui tournent deja sur `sidy-dev` n'ont **aucune** limite memoire (`docker stats` y affiche 7,57 GiB, la memoire totale de l'hote, comme limite de chacune). Quatre conteneurs de la pile du memoire n'en avaient pas non plus — `prometheus`, `node-exporter`, `cadvisor`, `grafana`, contrairement a `app`, `mlflow` et `detection` qui en portent une depuis les phases B et C. Sans plancher, une fuite dans l'un de ces quatre aurait pu faire tuer par le noyau (OOM killer) le plus gros processus de **l'hote entier** — potentiellement un conteneur de production (ex. `cia-invest-db`) plutot qu'un conteneur du memoire. Ajoute dans `docker-compose.yml` : `mem_limit` sur `prometheus` (${PROM_MEMORY:-768m}), `node-exporter` (${NODE_EXPORTER_MEMORY:-64m}), `cadvisor` (${CADVISOR_MEMORY:-256m}), `grafana` (${GRAFANA_MEMORY:-256m}), et `mlflow` abaisse de `1g` a `512m`. Les sept conteneurs de la pile ont desormais tous une borne memoire, ce qui n'etait vrai d'aucune des applications co-localisees.
- **Verifie, non modifie** : le trafic Locust de l'anomalie de saturation (`infra/injector/injector.py::_injecter_par_charge`) rejoint deja uniquement le reseau Docker interne de la pile (`--network memoire`) et cible `http://app:8000`, le nom de service du conteneur de test — jamais le reverse-proxy qui sert les applications de production. C'etait deja le cas avant le 14/11/2026 (commentaire en l'etat dans le code : « le seul conteneur d'injection qui a besoin du reseau de la pile »), donc aucun changement n'etait necessaire sur ce point ; seule la verification est nouvelle.
- **Surveillance humaine qui reste, faute de garde-fou automatique** : un `free -h` quotidien pendant les dix jours d'enregistrement, et `make stop-chaos` si la memoire disponible descend sous 1 Go. Rien dans le pipeline ne fait cette verification a la place de Sidy : elle n'est pas codee parce qu'une alerte supplementaire sur l'hote lui-meme sortirait du perimetre de l'experience (le detecteur surveille l'appli de test, pas l'hote de production).

## 2026-11-14 — D46 : pic_cpu et fuite_memoire passent par le processus de l'appli, pas par un conteneur stress-ng

- **Constat** : `docker ps` sur le serveur de demonstration montre que cAdvisor (derniere image, v0.52.1) ne remonte **aucun** conteneur, y compris `memoire-app` lui-meme. Le Docker Engine du serveur (29.9.2) utilise le magasin d'images par `containerd-snapshotter`, et cAdvisor ne sait pas retrouver le `rootfs` / les couches d'un conteneur avec ce magasin — bug amont confirme, non corrige a ce jour meme sur la derniere image. Consequence directe pour D45 : `cpu_appli`, `memoire_appli`, `reseau_entrant`, `reseau_sortant`, tous issus de cAdvisor par conteneur, seraient vides sur le serveur reel, alors meme que `cpu_appli`/`memoire_appli` sont marques `obligatoire: true` depuis la phase B — une session reelle echouerait au chargement.
- **Piege specifique a `pic_cpu` et `fuite_memoire`** : ces deux types injectent aujourd'hui via un conteneur `stress-ng` dedie (`moyen: conteneur`). Si ce conteneur reste invisible a cAdvisor, l'anomalie reste etiquetee (`data/labels/<run_id>.csv`) mais ne bouge **aucune** colonne enregistree : le rappel par evenement (§7) baisserait pour les quatre strategies a la fois, sans qu'aucune ne puisse y faire quoi que ce soit — exactement le piege deja identifie en D38 (une anomalie etiquetee mais invisible dans le flux mesure fausse la comparaison plutot que de la rendre difficile).
- **Choix** :
  1. `cpu_appli` et `memoire_appli` passent de metriques cAdvisor par conteneur a des metriques de **processus**, exposees par l'appli elle-meme via `prometheus_client.ProcessCollector` (`infra/app/metrics.py`) : `process_cpu_seconds_total` (en `rate`) et `process_resident_memory_bytes`, filtrees par `job="app"` (`configs/datasets/serveur.yaml`). Un seul worker uvicorn tourne par conteneur `memoire-app`, donc une seule serie par expression : pas d'agregation a faire entre processus. Noms de colonne inchanges, pour que le reste du pipeline (features, comparaison au SMD) n'ait rien a savoir du changement de source.
  2. `pic_cpu` et `fuite_memoire` deviennent `moyen: appli` par defaut (`configs/injection.yaml`) : l'injecteur appelle desormais le plan de controle de l'appli de test, comme `latence`/`erreurs` deja. Deux methodes ajoutees a `infra/app/chaos.py` : `Chaos.injecter_cpu` demarre un thread qui calcule en boucle pendant `duree_s` ; `Chaos.injecter_memoire` alloue progressivement jusqu'a un plafond fixe `PLAFOND_MEMOIRE_MO = 200.0` (Mio), nettement sous la limite `mem_limit: 512m` du conteneur `app`, puis libere a la fin. Les deux refusent une duree au-dela du plafond global de 600 s (`securite.duree_max_s`, D-anterieure, inchange). Le travail de fond interroge en continu (pas seulement a l'echeance) si son injection est toujours la courante active — meme mecanisme de sonde que `_subir_conteneur` pour les conteneurs — pour que `/chaos/reset` reste un vrai arret d'urgence et pas seulement une remise a zero des jauges.
  3. `infra/injector/injector.py::ENDPOINTS_APPLI` est etendu de `latence`/`erreurs` a `pic_cpu` (`/chaos/cpu`, cle `threads`) et `fuite_memoire` (`/chaos/memory`, cle `mo`) : `_injecter_par_appli` devient generique aux quatre types plutot que specifique a deux.
  4. `moyen: conteneur` (stress-ng) **reste code et teste**, documente dans `configs/injection.yaml` comme option ponctuelle hors session enregistree — utile pour un test de charge isole ou si l'hote de demonstration change un jour de magasin d'images. `limites` et `image_stress` restent donc dans la config, avec un commentaire explicite sur leur usage reduit a ce chemin optionnel.
  5. `reseau_entrant`/`reseau_sortant` (deja par conteneur depuis D45, donc deja aveugles au meme bug) passent de `obligatoire: true` a `obligatoire: false` dans `configs/datasets/serveur.yaml` : aucune metrique de processus ne les remplace (le reseau n'est pas un concept par processus en dehors d'un namespace reseau dedie, que l'appli n'a pas), mais la saturation reste visible par `requetes_par_s`, `latence_p50`/`latence_p95` et `requetes_en_vol`, qui ne dependent d'aucune des deux sources cassees.
- **Alternatives ecartees** : corriger ou contourner cAdvisor (mise a jour deja a la derniere version, bug amont confirme non corrige — rien a corriger cote depot) ; revenir a l'ancien magasin d'images Docker (`overlay2`) sur un serveur de production partage avec une vingtaine de conteneurs deja en service (changement d'infrastructure hors de portee du memoire, risque sur des applications de tiers) ; garder stress-ng comme seul chemin et accepter la perte de `pic_cpu`/`fuite_memoire` comme limite documentee (aurait fausse le rappel par evenement sur deux types d'anomalie sur cinq, la part la plus commode a corriger) ; mesurer le CPU/la memoire du conteneur stress-ng lui-meme plutot que celui de l'appli (ne repondrait pas a la question posee : le detecteur doit voir l'effet sur l'appli de test, pas sur le generateur de charge).
- **Raison** : la seule maniere de garder `pic_cpu` et `fuite_memoire` mesurables sur un hote ou cAdvisor est aveugle est de deplacer la charge **dans** le processus deja observe par une autre voie (le collecteur de processus, qui ne depend pas de cAdvisor). Le plafond de 200 Mio et la sonde continue d'activite reprennent exactement les deux garanties de securite deja exigees des conteneurs d'injection (limite memoire, arret d'urgence reel) sans les perdre en changeant de mecanisme.
- **Test(s) touche(s)** : `tests/test_app_test.py` (cinq tests ajoutes : demarrage et etiquetage du pic CPU, refus sans fil d'execution, demarrage et etiquetage de la fuite memoire, refus au-dela du plafond, `/chaos/reset` remet aussi CPU et memoire a zero) ; `tests/test_injector.py` (helper `_config_moyen_conteneur` ajoute pour garder une couverture du chemin conteneur optionnel sur les tests qui testent specifiquement stress-ng — limites, absence de privilege, systeme de fichiers en lecture seule, conteneur tue en cours, echec au demarrage ; les autres tests utilisant `pic_cpu`/`fuite_memoire` comme type d'injection quelconque sont passes a `appli=ApplieFactice()` ou a un autre type, `saturation`, quand ils ne testaient pas une propriete specifique au conteneur).
- **A exploiter au memoire** : le 6.3.3 (limites rencontrees) gagne un exemple concret de la difference entre une anomalie **etiquetee** et une anomalie **mesurable** — le piege de D38 observe une seconde fois, cette fois cote infrastructure reelle plutot que cote choix de features ; le 5.x (description du pipeline de demonstration) doit noter que l'injection de charge interne a l'appli est un choix delibere motive par une limite materielle de l'hote, pas une simplification du protocole d'injection lui-meme (les cinq types restent definis au meme endroit, §4.2 du cadrage, avec la meme duree et le meme horodatage).
